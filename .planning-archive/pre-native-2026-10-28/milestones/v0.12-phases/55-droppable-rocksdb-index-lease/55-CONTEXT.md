# Phase 55 Context: Droppable RocksDB index lease

**Milestone:** v0.12 / harness M002 S07 (last slice of M002)
**Requirements:** ROCK-01, PERF-GATE
**Depends on:** Phase 51 (optional Rocks feature, spike), Phase 54 (segments, manifest, chain; shipped)
**Run rules:** `docs/process/gsd-auto-contract.md` (RED first; oracle preservation; bench gate; CBM primary, GitNexus secondary outside M013)

## Locked decisions

- **D-01 (what Rocks is):** a droppable LEASE. RocksDB stores only locators and ids; the segmented log is the truth. Deleting the Rocks directory changes no answer. Rocks never stores an event payload, a commit frame, a disposition, a term meaning, or a hash chain. It is NOT wired into `Runtime`, `store::open`, `Persister`, fold or hydrate; it stays an optional cargo feature, so the default build and the bench never compile RocksDB.
- **D-02 (shape):** new module `crates/kutha-runtime/src/rocks_index.rs` behind a NEW feature `rocks-index` (`= ["dep:rocksdb"]`, same optional dependency, `default-features = false`). The Phase 51 `rocks_spike.rs` (jsonl offsets) and its `m002_rock00.rs` oracles stay as they are for legacy/export files; the feature `rocks-index-spike` keeps working. If one shared feature is simpler, the executor may alias them but must not drop any ROCK-00 oracle.
- **D-03 (layout):** keys are prefixed: `e:` + 16-byte `EventId` -> `(segment seq u32, byte offset u64, frame length u32)` big-endian; `d:` + UTF-8 `delivery_key` -> 16-byte `EventId` of the Assert that holds it (same winner rule as `Runtime`'s `by_delivery_key`; read `admission.rs`/`fold` to copy the exact rule for retracted or corrected claims); `m:v` format version; `m:tip` = `(sealed manifest tip chain hex, event count, last EventId)` of the log the index was built from.
- **D-04 (API):** `SegmentIndex::build(store_dir, rocks_dir)`; `SegmentIndex::open_or_rebuild(store_dir, rocks_dir)` (valid iff `m:tip` equals the current log tip, otherwise drop the directory and rebuild); `catch_up` that indexes only events after the recorded position when the log only grew (append-only segments, same sealed prefix); `locate(id)`, `get_event(id)` (reads the frame from the segment by locator and re-verifies its CRC and that the decoded id equals the key), `by_delivery_key(key)`. A locator that points at a frame whose id differs is `InvalidData` (stale or corrupt index), and `open_or_rebuild` treats it as invalid.
- **D-05 (build input):** build from the verified segmented log (reuse the segment reader; do not re-parse jsonl); legacy dirs are rejected with `InvalidData` "run store::migrate first". Uncommitted suffix: index the committed prefix only (same `committed_prefix` as `open`).
- **D-06 (governor, first task, own commit):** `freeze-rocks` currently allows `rocksdb` only while Active Milestone is M002; the milestone ends after this slice and the check would fail. Replace the time-boxed rule with a durable one: `rocksdb` may appear in `crates/*/Cargo.toml` only as an optional dependency (`optional = true` on the same line) and never in the root `Cargo.toml` `[workspace.dependencies]` as a non-optional entry; keep the other two freeze checks unchanged. Prefer existing kinds (see `.kutha/META.md`); the Phase 51 `unless_file_contains` field may be removed from use but its code and tests stay unless nothing else needs them. Update pytest `FreezeDepTests`, the selftest mutation and the check message (Thaw map text is the controller's). The default `cargo tree -p kutha-runtime --offline` must still show no rocksdb.
- **D-07 (oracles, RED first)**, in `crates/kutha-runtime/tests/m002_rock01.rs` (`#![cfg(feature = "rocks-index")]`): `index_answers_equal_the_log` (every event id locates and `get_event` equals the log event; absent id is `None`); `delivery_key_index_equals_runtime_map` (index answers equal `Runtime`'s delivery-key map for kept, retracted and corrected cases); `dropping_rocks_dir_changes_no_answer`; `stale_index_is_rebuilt` (append through `Persister`, then `open_or_rebuild` reflects the new events; tamper `m:tip` -> rebuild); `catch_up_indexes_only_the_tail`; `locator_pointing_at_wrong_frame_is_invalid_data`; `rocks_values_hold_no_payload` (scan every key and value: prefixes in {e:, d:, m:}, value lengths are fixed locators/ids/meta, no JSON, no term string other than the delivery_key key material); `legacy_dir_rejected_until_migrate`; `uncommitted_suffix_is_not_indexed`; `multi_segment_store_locates_across_rollover` (lowered rollover seam); `default_build_has_no_rocksdb` is a recorded command, not a test.
- **D-08 (kill-mutations the verifier will run):** index value includes the payload; locate without CRC/id re-check; skip the `m:tip` staleness check; `catch_up` re-indexes from zero but reports tail only; delivery_key winner picks the first instead of the live one; index uncommitted suffix; build from jsonl; Rocks write inside `Persister`.
- **D-09 (docs):** ADR-010/012 Evidence lines dated 2026-10-04 (ROCK-01: lease layout, rebuild rule, what Rocks never stores; statuses stay **Proposed**); `docs/architecture/m002-cloud-kernel-io-intake.md` build record gets index build and lookup timings for a 10k-event segmented store; `honeycomb.yaml` restage line; CHANGELOG entry in the last commit. Residuals to state: not wired into Runtime (no consumer yet), single reader/writer, index rebuild cost is O(N), cold build of RocksDB ~5.5 min.
- **D-10 (bench):** only a feature-gated module changes under `crates/` plus Cargo.toml feature lines; default code paths are untouched. Run one interleaved pair set (2 pairs) of `ingest_plain.n`/`as_of.n`/`open.n` base vs head to confirm, separate worktrees and separate absolute target dirs, clean up afterwards (`git worktree list` must show only the main tree). Over 10 percent on medians is a stop.
- **D-11 (roles):** verifier is not the executor; the controller owns STATE, README lease row, CHANGELOG lease entry, `.kutha/ROADMAP.md`, REQUIREMENTS; no `55-VERIFICATION.md` from the executor.

## Out of scope

Wiring Rocks into `Runtime` or `open`, using Rocks for reads in the hot path, ADR-080/081, Cypher, HNSW, vacuum, multi-writer, any change to segments, chain, commit rules or Event/Op/fold.
